     Plan: multi-module nwn-manager + wiki generator

     Context

     Today nwn_manager is a single-module workspace: the repo itself contains
     bin/nwn-manager, nasher.cfg, and (in the v1.0 layout used by
     /home/james/GIT/nwn_homers_lotr) a flat src/ of ~7K unpacked GFF/JSON +
     .nss files. That couples the tool to one module project. The user
     wants:

     1. The tool to manage many modules. Each module lives in its own project
     folder; nwn_manager is just the CLI.
     2. Clean separation inside a project folder: unpacked module data goes in
     unpacked/ (was src/), so other project artifacts (notes, the
     generated wiki, scratch scripts) can sit alongside without bleeding
     back into the repack.
     3. A new wiki generator that, given a project's unpacked/ tree, builds
     a static multi-page site with: indexed creature/item stats, one page
     per area (with that area's spawns, loot, NPCs, stores), and a giant
     interactive map of all areas linked by their transitions, where
     clicking an area jumps to that area's page.
     4. README updated to describe the new multi-module workflow and the wiki.

     The example v1.0 module at /home/james/GIT/nwn_homers_lotr (286 areas,
     ~3K items, ~550 creatures, ~2.3K scripts, CEP 2 based) is the realistic
     test target — the wiki must scale to that.

     Approach

     1. Restructure project layout

     Per-module project folder (created anywhere, not under nwn_manager):

     my_module/
       nasher.cfg              # sources: unpacked/**, rules: * → unpacked
       unpacked/               # was src/ — all GFF JSON + .nss
       wiki/                   # generated; gitignored by default
       dist/                   # nasher build output; gitignored
       .nasher/                # nasher cache; gitignored
       .gitignore              # /dist, /.nasher, /wiki, *.ncs, *.mod
       README.md               # generated stub describing the module

     Key change: nasher [package.sources] include and [package.rules]
     both point at unpacked/ instead of src/. Anything outside
     unpacked/ is invisible to nasher pack and will not be reimported.

     2. CLI: bin/nwn-manager

     Operate on the current working directory as the project root (look up
     the tree for a nasher.cfg the way git does for .git). Subcommands:

     ┌──────────────────────┬──────────────────────────────────────────────────┐
     │         Cmd          │                   What it does                   │
     ├──────────────────────┼──────────────────────────────────────────────────┤
     │ nwn-manager init     │ Create project dir, write nasher.cfg with        │
     │ <project-dir>        │ unpacked/ rules, run nasher unpack to populate   │
     │ <module.mod>         │ unpacked/, write .gitignore and a stub           │
     │                      │ README.md.                                       │
     ├──────────────────────┼──────────────────────────────────────────────────┤
     │                      │ Refresh unpacked/ from the .mod. If no path      │
     │ nwn-manager unpack   │ given, re-use the last-used path stored in       │
     │ [<module.mod>]       │ .nasher/last_source (or read from nasher.cfg's   │
     │                      │ [target] install if set).                        │
     ├──────────────────────┼──────────────────────────────────────────────────┤
     │ nwn-manager repack   │ Run nasher pack. If [target] install is set in   │
     │ [args…]              │ nasher.cfg, copy the built .mod there. (Replaces │
     │                      │  the per-project repack.sh.)                     │
     ├──────────────────────┼──────────────────────────────────────────────────┤
     │ nwn-manager wiki     │ Generate the wiki under <project>/wiki/.         │
     │ [--out <dir>]        │                                                  │
     ├──────────────────────┼──────────────────────────────────────────────────┤
     │ nwn-manager --help   │ Updated usage text.                              │
     └──────────────────────┴──────────────────────────────────────────────────┘

     The bespoke unpack.sh/repack.sh per project become unnecessary: the
     install destination (with apostrophe-symlink workaround) moves into
     nasher.cfg ([target] install = "/path/to/Module.mod") and the CLI
     handles the symlink-to-/tmp trick before invoking nwn_erf.

     3. Wiki generator: bin/nwn-wiki (Python 3, stdlib only)

     A separate executable so it can be invoked directly or via
     nwn-manager wiki. Pure stdlib (no pip install step) keeps install
     parity with the rest of the toolchain. The wiki regenerates only
     when explicitly requested (nwn-manager wiki); repack stays fast
     and pure — it does not trigger a wiki rebuild.

     Pipeline:

     1. Parse unpacked/: walk the tree, classify by extension, load
     each JSON. Build in-memory tables keyed by ResRef:
       - areas[resref] ← .are.json (Tag, Name, Tileset, Width, Height,
     event scripts)
       - git[resref] ← .git.json (placed Creature/Door/Encounter/
     Placeable/Sound/Store/Trigger/Waypoint lists)
       - creatures[resref] ← .utc.json (stats, class, faction, scripts,
     conversation, equipment)
       - items[resref] ← .uti.json (BaseItem, Cost, properties)
       - doors[resref] ← .utd.json (incl. LinkedTo waypoint tag)
       - triggers[resref] ← .utt.json (incl. LinkedTo)
       - encounters[resref] ← .ute.json (CreatureList → spawn pool)
       - placeables[resref] ← .utp.json (incl. their ItemList for
     chests)
       - stores[resref] ← .utm.json (StoreList inventory pages)
       - waypoints[resref] ← .utw.json
       - dialogs[resref] ← .dlg.json (just for NPC → conversation
     reverse lookup; do not render full trees in v1)
       - module_ifo ← module.ifo.json (area list, hooks, HAKs, TLK,
     start area)
       - journal ← module.jrl.json
       - factions ← repute.fac.json
     2. Build derived indexes:
       - Waypoint tag → area: scan every .git.json's
     WaypointList; map Tag → containing area resref.
       - Area transitions: for each area, walk .git.json's
     TriggerList and Door List — for each placed instance whose
     blueprint (or embedded struct) has LinkedTo set, resolve the
     destination via the waypoint-tag map → produces a directed edge
     (src_area, dst_area, kind) where kind ∈ {trigger, door}.
       - Per-area NPC list: every Creature List instance, joined to
     creatures[] for stats. Hostile vs friendly via FactionID →
     factions.RepList lookup against the PC faction (id 0).
       - Per-area encounter spawns: EncounterList → encounter
     blueprint → CreatureList.
       - Per-area chest loot: Placeable List instances whose
     ItemList is non-empty → enumerate items by ResRef.
       - Per-area stores: StoreList → store blueprint → StoreList
     pages → enumerated items.
     3. Render HTML (jinja-style with Python string.Template or
     manual f-strings — stdlib only, no Jinja install). Output:

     wiki/
       index.html                # module overview + giant map
       areas/<resref>.html       # one per area
       creatures/index.html      # sortable table of all creatures
       creatures/<resref>.html   # per-creature page
       items/index.html
       items/<resref>.html
       stores/<resref>.html
       factions.html
       journal.html
       assets/style.css
       assets/map.svg            # the giant area map
       assets/data.json          # raw graph for any future client-side
     4. The giant map: a single SVG generated server-side.
       - Nodes = areas (rect labelled with Name, sized by tile area).
       - Edges = transitions (color-coded: trigger vs door).
       - Layout: simple force-directed (Fruchterman-Reingold,
     ~200 iterations, all-pure-Python — fine for ≤500 nodes).
       - Each <rect> wrapped in <a xlink:href="../areas/<resref>.html">
     so clicking jumps to the area page. Pure static SVG, no JS.
       - Edges to/from "out of module" destinations (waypoint tag with no
     home area) drawn to a sentinel "external" node so dead links are
     visible but don't clutter the layout.
     5. Per-area page sections:
       - Header: name, tag, tileset, dimensions, event-script links.
       - Mini-map cutout: zoomed crop of the giant SVG centred on this
     node (optional v1.5 — out of scope for first cut).
       - Adjacent areas (in/out transitions, with kind).
       - NPCs: table of friendly/neutral creatures with stats summary +
     link to full page; conversation resref linked.
       - Hostile residents: same, separated.
       - Encounters: table of (encounter, spawn pool, max creatures, 
     difficulty).
       - Chests / loot: table of placeable → contained items.
       - Stores: per-store inventory (5 pages).
       - Triggers/doors: full transition list.
     6. Per-creature / per-item pages: dump key fields in a readable
     table. For items: include BaseItem row name (resolve via a
     small bundled baseitems.2da lookup table — bundled JSON in
     bin/wiki_data/). For creatures: include resolved class names
     (similar bundled lookup for classes.2da).
     7. Performance: the example module is ~5K JSON files. Single-pass
     parse + in-memory build should run in a few seconds with stdlib
     json; render is O(files). Target: full-module wiki in under 30s
     on a laptop.

     4. Files to create / modify

     - MODIFY bin/nwn-manager — new subcommand structure, project
     discovery (walk-up for nasher.cfg), absorb the symlink workaround
     for apostrophes, drive unpacked/ instead of src/.
     - CREATE bin/nwn-wiki — Python 3 wiki generator (stdlib only).
     - CREATE bin/wiki_data/baseitems.json,
     bin/wiki_data/classes.json,
     bin/wiki_data/racialtypes.json,
     bin/wiki_data/appearance.json — minimal 2DA → name lookup tables
     for human-readable wiki output. Hand-curated subsets sourced from
     the public NWN 2DA files (CEP overrides noted but not bundled).
     - CREATE bin/wiki_assets/style.css — base wiki stylesheet,
     copied verbatim into <project>/wiki/assets/.
     - MODIFY README.md — rewrite the "Layout" and "Usage" sections
     for multi-module + project folders + the new wiki subcommand,
     plus a short "Wiki" section explaining the generator's output.
     - MODIFY .gitignore — no change needed in nwn_manager itself
     (the manager repo never holds module data); the per-project
     .gitignore is generated by nwn-manager init.
